# 가사 절/후렴 구조화 스킬 (v2 설계 초안)

**상태: DRAFT — 설계 승인 후 구현**

마커가 없거나 불완전한 본문에서 절/후렴 경계를 자동 추론하여 `[1절]`, `[후렴]` 등 스펙 마커를 **본문 문자열 안에 인라인**으로 부여한다.

## v2 스키마 차이점 (v1과 비교)

v1: `가사.본문`(단일 문자열) + `가사.절별`(dict) + `가사.절구조`(문자열) 3필드 동기화 필요
v2: **`가사`(단일 문자열) 하나만**. 절 구조는 본문 내 인라인 마커(`[1절]`, `[후렴]`)로 표현.

따라서 이 스킬은 **본문 문자열에 마커 라벨링만 부여**한다. 별도 dict/구조 필드를 만들지 않음.

## 데이터 흐름 (v2)

```
편집 대상: data/source/곡정보.xlsx의 '가사' 시트 (B열, 본문 단일 셀)
입력: 마커 없는 또는 불완전한 본문
출력: 같은 셀에 마커 부여된 본문
후속: python scripts/rebuild.py
```

xlsx 잠금 시 "엑셀을 닫아주세요" 안내. clean-lyrics와 동일 패턴.

## 기존 스킬과의 역할 구분

| 스킬 | 역할 | 대상 |
|---|---|---|
| `/clean-lyrics` | 본문 정리(오염·슬래시·빈 줄·짧은 절 병합) | 마커 유무 무관 |
| **`/structure-lyrics`** (신규, DRAFT) | **구조 추론** — 마커가 없는 텍스트에서 절/후렴 경계 감지 후 마커 부여 | clean-lyrics 후, 마커가 없거나 비정형인 곡 |

권장 순서:
```
crawl-lyrics → apply_to_xlsx → clean-lyrics → structure-lyrics → rebuild
 (본문 확보)    (xlsx 적용)    (오염 정리)     (마커 부여)      (JSON 재빌드)
```

## 적용 대상

- 본문에 마커 `[` 가 전혀 없는 곡
- 또는 마커가 부분적이라 절 번호·후렴 구분이 깨진 곡
- 사용자가 웹/OCR로 갓 입력한 원본 텍스트

## 2단계 추론 파이프라인

### Stage 1: 결정적 규칙 (deterministic pass)

입력 텍스트에서 다음 휴리스틱으로 구조 후보 생성:

**R1. 블록 분리**
- 빈 줄(`\n\n` 이상)로 블록 분리
- 빈 줄이 없으면 전체를 한 블록으로 간주 → Stage 2로 이관

**R2. 반복 구절 감지 (후렴 후보)**
- 각 블록의 첫 2~3어절과 줄 수/글자 수를 지문(fingerprint)으로 계산
- 동일 지문이 2회 이상 등장 → 해당 블록을 `[후렴]` 후보로 태깅
- 유사도 측정: 자카드 계수(어절 집합) ≥ 0.7 또는 편집거리 ≤ 20%

**R3. 절 번호 부여**
- 후렴이 아닌 블록을 등장 순서대로 `[1절]`, `[2절]`, ... 배정
- 중복 번호 방지

**R4. 마커 인라인 삽입**
- 각 블록의 첫 줄 앞에 `[N절]` 또는 `[후렴]` 토큰 삽입
- 블록 사이는 단일 줄바꿈으로 정리 (이중 빈 줄 제거)

**R5. 구조신뢰도 점수 산출**
- 블록 수, 후렴 일치도, 절 길이 편차로 `S_struct` (0~1) 계산
- ≥ 0.8: 자동 확정 후보
- 0.5~0.8: 사용자 확인 필요
- < 0.5: Stage 2로 이관

### Stage 2: LLM 보정 (ambiguous cases)

Stage 1 구조신뢰도 < 0.5 또는 블록 분리 불가한 경우:

**입력**: 원 텍스트, 제목, 작곡자
**출력**: 다음 JSON (런타임만, 저장 안 함)

```json
{
  "마커부여본문": "[1절] ...\n[후렴] ...\n[2절] ...\n[후렴] ...",
  "근거": "2-3행마다 반복되는 '주님 찬양합니다' 구절이 후렴. 블록 경계는 운율 변화로 추정.",
  "구조신뢰도": 0.72,
  "불확실": ["3절 경계 애매", "브릿지로 분류할 수도 있음"]
}
```

**프롬프트 원칙**
- "본문만" 기반으로 판단, 외부 검색 금지 (외부 검색은 별도 deprecated 스킬)
- 불확실 시 절 번호를 늘리지 말고 `불확실` 필드로 보고
- Copyright/코드심볼 등 오염 제거는 하지 않음 (`/clean-lyrics` 역할)

## 사용자 확인 워크플로우

자동 덮어쓰기 금지 — 항상 사용자 승인 관문 통과:

1. 스킬 실행 → 제안 본문을 임시 산출물(`data/structure_proposals/{번호}.txt`)에 저장
2. 사용자에게 원본 vs 제안 비교 출력
3. 승인 시 `apply_to_xlsx.py`와 동일한 패턴으로 곡정보.xlsx의 `가사` 시트 셀 갱신
4. 거부 시 제안 파일 삭제

## 실행 (제안 — 미구현)

```bash
python scripts/structure_lyrics.py 5             # 단일
python scripts/structure_lyrics.py 1-100         # 범위
python scripts/structure_lyrics.py 미구조화      # 마커 없는 곡만
```

## 데이터

- 입력: `data/source/곡정보.xlsx`의 `가사` 시트 (읽기)
- 중간 산출물(승인 대기): `data/structure_proposals/{번호}.txt`
- 최종 반영: 사용자 승인 후 `data/source/곡정보.xlsx`의 `가사` 시트 셀 갱신

## 원칙

- **xlsx만 수정** — songs.json 직접 갱신 금지 (다음 rebuild에 덮어쓰여짐)
- **제안만, 자동 덮어쓰기 금지** — 항상 사용자 승인
- **마커는 본문 인라인** — v2에선 별도 절별/절구조 필드 없음. `[1절] ...\n[후렴] ...` 형식 본문 한 셀로 완결
- **외부 호출 없음** (Stage 2 LLM은 로컬 대화 맥락 내)
- **clean-lyrics와의 분담 유지** — 본문 정리는 안 함

## 미해결 질문 (구현 전 확인 필요)

1. **브릿지/코다 감지**: 3회 이상 반복되지 않지만 후렴 사이에 끼는 블록을 자동으로 브릿지로 볼지?
2. **절 순서 확정**: 원문이 `후렴→1절→후렴→2절` 순인 경우 그대로 기록할지, `1-2-후렴` 정규화할지?
   - v2에서는 본문 순서가 그대로 표시되므로 **원문 순서 보존이 자연스러움**
3. **제안 파일 경로**: `data/structure_proposals/` 디렉토리 신설 적정성?
4. **Stage 2 프롬프트**: 별도 파일로 분리할지?

## 검증 방법

- 이미 수작업 검수된 곡 20개를 입력으로 주고, 스킬 출력 본문과 정답 본문의 마커 위치 일치율 측정
- 목표: 1차(결정적) 70% 이상, 2차(LLM 보정 포함) 90% 이상
