# S-011: 사용 경험 데이터 사이드카 도입 (ADR-008)

**상태:** 완료
**기간 시작:** 2026-04-30
**기간 종료:** 2026-04-30

## 목표

성가대 운영의 누적 경험을 추천에 반영할 수 있도록, **카탈로그(곡정보.xlsx)와 분리된 별도 도메인**으로 4개 사이드카 저장소를 도입한다.

1. **선곡표 묶음 누적**: 매달 다듬어 쌓이는 미사 선곡을 엑셀 형태로 직접 편집·관리.
2. **곡별 사용경험 집계**: 학생들과 부딪쳐 본 인상(난이도·음역·떼창적합·반주필수·메모)을 누적해 추천 LLM의 1차 인풋으로.
3. **소감 raw 로그**: 미사 후 곡별/미사 전체 인상을 시점별 보존. 곡별 집계 갱신은 사용자 승인 게이트로.
4. **추천 흐름 분리**: `/recommend-hymns` Step 7의 csv 직접 쓰기를 신규 `/log-setlist` 스킬로 위임. 회고는 `/log-impression` 스킬로 구조화.

## 배경

- v2.1 도입 후 카탈로그(곡정보.xlsx)는 단일 SSoT로 잘 정착했으나, **운영 경험 데이터**(부른 곡·소감·체감 난이도)는 어디에도 저장되지 않음.
- `색인.비고`(v2.1 부활)는 한 줄 자유 메모라 누적·시계열을 담기 부적합.
- `선곡기록.csv`는 행 단위 누적이라 "한 달치 묶음을 다듬는" 흐름과 안 맞음.
- 카탈로그 빌드 파이프라인(`rebuild.py`)에 운영 데이터를 끼워 넣으면 도메인 오염.

→ 운영 경험은 카탈로그와 분리된 별도 도메인으로 두되, 추천 LLM이 빠르게 참조할 수 있는 포맷이 필요.

### B. 데이터 파일 신설 ✅
- `data/source/선곡표.xlsx` (시트 `선곡`, Tall 형식 7컬럼)
- `data/song_impressions.json` (사이드카, 곡별 enum + 메모 + watermark)
- `data/impression_log.jsonl` (append-only raw)
- `.gitignore` 3개 모두 추가
- `scripts/init_setlist_xlsx.py` (1회 초기화 스크립트)

### C. 서버 API 6개 신규 + GET 머지 ✅
- `server/app.py` `_adapt_v2_to_v1`이 `song_impressions.json` 머지해 곡 객체에 `사용경험` 키 노출
- `GET /api/impressions/{num}` — 곡별 집계 + 최근 raw 로그 N건
- `PUT /api/impressions/{num}` — 양방향 기록(집계 + audit 라인 + watermark 이동)
- `POST /api/impressions/reflect` — 회고 후 집계 갱신 + watermark 지정 이동
- `POST /api/impression-log` — raw 한 건 append (id/시각 서버 생성)
- `GET /api/setlist` — 선곡표.xlsx 조회
- `POST /api/setlist` — 행 append (xlsx 잠금 시 409)

### D. viewer UI 사용경험 편집 블록 ✅
- `viewer/index.html` 메타정보 아래 새 섹션:
  - 난이도/음역 select (3-way)
  - 떼창적합/반주필수 3-state 라디오 (Y/N/미정)
  - 메모 textarea
  - "사용경험 저장" 버튼 → PUT
  - 최근 소감 로그 5건 자동 표시
- 양방향 기록: 저장 시 audit 라인 자동 append + watermark 이동

### E. `/log-setlist` 스킬 ✅
- 모드 A: `/recommend-hymns`에서 구조화 페이로드로 호출
- 모드 B: 사용자가 단독으로 자연어 입력 → 표 확인 → POST `/api/setlist`
- 곡명 자동 채우기(`songs_index.json`), xlsx 잠금 시 안내

### F. `/log-impression` 스킬 ✅
- Step A: 회고할 미사 선택 (선곡표 최근 행 후보 제시 또는 직접 입력)
- Step B: 곡별/미사 전체 분기
- Step C: POST `/api/impression-log`로 raw append
- Step D: 곡별 미반영 카운트(`last_reflected_id` 이후) 표시 → 승인 게이트 → POST `/api/impressions/reflect`로 집계 갱신 + watermark 이동
- 핵심 정책: 자동 갱신 절대 금지, raw는 수정·삭제 불가(정정도 새 라인 append)

### G. `/recommend-hymns` 보강 ✅
- 데이터 소스에 사용경험·선곡표·소감 로그 추가
- Step 2-4: 미사 전체 소감 요약을 옵션 컨텍스트로 주입
- Step 3: 중복 회피 기준 `선곡기록.csv` → GET `/api/setlist`
- Step 4 우선순위 8번: 사용경험 시그널 (떼창/반주필수/난이도)
- Step 5 선정 이유 예시에 `사용경험.*` 근거 추가
- Step 7: csv 직접 쓰기 제거 → `/log-setlist` Skill 호출 위임

## 회고

### 잘된 점
- **plan 다듬기 4회**가 비용보다 가치가 컸음. 첫 plan은 v1.1 schema bump였으나 실제 v2.1 + 빌드 산출물 구조를 모르고 잡혔던 것 — 코딩 전에 발견해서 큰 재작업 회피.
- **양방향 기록(viewer 편집 → audit 라인) + watermark** 구조가 단순한 "사이드카에 저장" 보다 의도 보존이 강함. 사용자가 "왜 갱신됐는지" 추적 가능.
- **자동 검증 스크립트(`_verify_adr008.py`)** 25개 항목으로 회귀 안전망 확보. 향후 사이드카 구조 변경 시 빠른 회귀 검증 가능.

### 개선
- **스프린트 추적 누락**: 작업 시작 시점에 새 스프린트로 등록해야 했음. 사용자 지적 후 소급 등록. 다음부터는 plan 단계에서 "이게 어떤 스프린트인지" 결정하고 진입.
- **터미널 출력 인코딩**: Windows cp949에서 한글 깨짐. 검증 스크립트는 `sys.stdout.reconfigure(encoding="utf-8")`로 해결 가능했지만 하나만 해도 결국 기본 시스템 인코딩 의존.

### 교훈
- **단일 SSoT 원칙은 도메인 한정**으로 재해석 가능. 카탈로그(곡의 정체성)와 운영 데이터(사용 경험)는 같은 SSoT 원칙을 공유하지 않아도 됨. ADR에 이 구분을 명시한 것이 향후 비슷한 사이드카 추가 시 일관성 유지에 도움.
- **승인 게이트 + watermark** 조합은 "회고만 하고 갱신은 미루기"가 자연스러워짐. 누적된 미반영분이 다음 회고에서 자동 노출되므로 사용자 페이스대로 진행 가능.
- **빌드 외부 사이드카**가 가져오는 자유: viewer가 직접 써도 안전, rebuild에 영향 없음, 락 충돌 없음. xlsx 락 처리만 곡정보.xlsx와 동일 패턴(`PermissionError → 409`)으로 통일.

### 후속 작업 (별도 진행)
- 본 스프린트가 만든 인프라의 실전 사용 — `/log-impression`을 실제 미사 후 호출, `/log-setlist`로 한 달치 선곡 누적, 추천 시 사용경험 가중치 효과 관찰. 이슈로 등록할 만한 항목은 발견 시 ISSUES.md에 추가.
- 장기: raw 로그가 매우 길어질 때 압축·요약 정책 필요 (현재 스코프 외).
