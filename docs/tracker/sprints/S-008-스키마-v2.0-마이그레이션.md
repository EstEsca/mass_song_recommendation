# S-008: 스키마 v2.0 마이그레이션 + 운영 도구 재편

**상태:** 완료
**기간 시작:** 2026-04-25
**기간 종료:** 2026-04-25

## 목표

1. **스키마 단순화**: songs.json v1.0의 누적된 복잡도(신뢰도·외부ID·가사 중첩 6필드·색인 6필드)를 정리하여 v2.0으로 메이저 범프.
2. **편집 SSoT 일원화**: JSON 직접 편집·엑셀 편집 이원화를 종식. 사용자 편집은 `data/source/곡정보.xlsx` 한 파일에서만.
3. **3계층 데이터 분업**: 편집(xlsx) → 소비(songs.json) → 뷰(songs_index.json) → LLM 입력(런타임 Wide TSV) 4단계 자동화.
4. **운영 도구 재편**: 가사 관련 스킬 9종을 v2 흐름에 맞춰 정리 (3 리팩토링 + 6 deprecated). 신규 도구(add-tag, label-lyrics) 신설.

## 배경

- 운영 4개월간 누적된 v1.0 구조의 한계:
  - 신뢰도·외부ID 등 실사용 없는 필드가 매 빌드·매 스킬에서 노이즈
  - JSON 에디터(server/)와 엑셀이 분리돼 일관성 유지 어려움
  - `recommend-hymns`가 매주 ~30K 토큰을 LLM에 부어야 했음
- v1 색인 데이터 자체에 오염 발견: `색인.전례별`에 작곡자 이름이 86건 잘못 입력됨
- `feedback_no_auto_field_fill` 정책은 유지하되, 도구는 사용자 명시 요청 시 빠르게 적용 가능하도록 개선 필요

## 범위 — 7-Stage 구성

### Stage A. 스키마 v2.0 마이그레이션 ✅
- ADR-006 작성, schema.md v2.0 + vocab.md 신규
- 곡 객체: 6 최상위(번호·제목·작곡자·분류·색인·가사), 색인 8카테고리(요약+성경/성월/시기/대축일/역할/느낌/키워드/곡모음집)
- 신뢰도·외부ID·가사 하위 5필드 폐기
- `scripts/migrate_v1_to_v2.py`로 in-place 변환 + 신뢰도 백업 xlsx 생성

### Stage B. xlsx SSoT 빌드 파이프라인 ✅
- `data/source/곡정보.xlsx` (4시트: 곡목록·요약·색인 tall·가사) 생성
- `scripts/build_songs_json.py` (xlsx → songs.json)
- `scripts/build_song_index.py` (songs.json → songs_index.json, 가사 제외)
- `scripts/rebuild.py` (일괄) + sha256 동기화 검증
- round-trip 테스트 통과 (곡 일치 차이 0건)

### Stage C. 에디터 v2 어댑터 ✅
- `server/app.py`에 v2 ↔ v1 어댑터(`_adapt_v2_to_v1`)
- 가사 본문 PUT → 곡정보.xlsx 가사 시트 직접 편집
- 자동 rebuild 호출 / xlsx 잠금 시 409 Conflict
- viewer/index.html(1741줄) 무수정으로 호환
- viewer/server.py deprecated 처리

### Stage D. 가사 스킬 v2 정리 ✅
- **리팩토링 3개**: clean-lyrics, crawl-lyrics, structure-lyrics (xlsx 직접 편집 + 자동병합 비활성화)
- **deprecated 6개**: validate-lyrics-format, get-lyrics-data-local, repair-lyrics, extract-sheet-lyrics, enrich-liturgy-index, fix-lyrics-format
- 신규: `scripts/crawler/apply_to_xlsx.py` (jsonl → xlsx)
- 레거시: `scripts/crawler/_merge.py` deprecated 헤더 추가

### Stage E. recommend-hymns v2 재작성 ✅
- 모드 A(Classic) + 모드 B(Funnel, experimental) 토글
- `scripts/filter_candidates.py` (Hard filter + Soft scoring + Diversity)
- `scripts/serialize_candidates.py` (JSON → Wide TSV, ~5배 압축)
- boost_tags(세션 가중치) 지원
- 주당 토큰 39K → ~8~10K 목표

### Stage F. add-tag 스킬 신설 ✅
- 자연어 "N번 곡에 X 태그 추가" → `scripts/add_tag.py`로 곡정보.xlsx 색인 시트 append
- vocab 검증(느낌/역할/시기/성월/성경 정규형식) + 중복 체크
- 단일/복수/범위 곡 지원

### Stage G. label-lyrics 스킬 + apply_labels ✅
- LLM이 가사 본문 분석 → 요약(40~60자)·느낌(vocab)·키워드 제안
- 사용자 승인 → `scripts/apply_labels.py` → 곡정보.xlsx 요약/색인 시트 반영
- vocab 위반 거부, 중복 skip

## 회고

### 잘된 점
- **점진 검증**: 각 Stage 끝마다 검증 스크립트로 회귀 방지. round-trip 0건 차이가 큰 안전장치였음.
- **어댑터 패턴**: 1741줄 viewer/index.html을 건드리지 않고 v2로 이전. 백엔드 어댑터만으로 충분.
- **deprecated 처리**: 무리하게 9개 스킬을 다 리팩토링하지 않고 핵심 3개에 집중, 나머지는 명확한 경고로 표면만 막음.
- **vocab 활용**: feeling·role 등의 vocab 검증이 add-tag·label-lyrics·migrate에서 일관되게 작동.

### 다음 스프린트로 넘기는 항목
- **495곡 라벨링(#36)**: 별도 작업. recommend-hymns 모드 B 정확도의 핵심 변수.
- **모드 B 회귀 테스트(#37)**: 실제 주일 추천을 모드 A vs B로 비교, 겹치는 곡 ≥60% 검증.
- **Stage H(3개월 후)**: 임베딩·역색인·전례력 캐시는 사용 데이터(fail case)에 따라 재평가.

### 교훈
- 큰 마이그레이션은 **번호 매핑 데이터의 오염**을 만난다. v1 `색인.전례별`에 작곡자 이름 86건. 마이그레이션 스크립트가 vocab 검증으로 자동 정리하면서 보고에 포함시킨 것이 좋았음.
- **자동 빌드 + 어댑터**가 결합되면 사용자 행동 변화 비용 거의 없음. 사용자는 엑셀에서 편집하고 에디터에서 가사 보고 → 자동으로 JSON 동기화.
- 스킬 deprecated 시 frontmatter `status: deprecated`는 VS Code agents 규격에 unsupported. description 앞에 `[DEPRECATED — v2 미대응]`을 다는 게 호환성 면에서 안전.
