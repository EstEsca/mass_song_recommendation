## C-04: 작업 호흡 길이 조절

**카테고리:** 작업 방법론

### 도입 시 이점

- 행잉 없이 안정적 진행
- 복귀해도 맥락 이어짐
- Claude 컨텍스트 윈도우 효율 사용

### 도입 시 비용

## C-05: 벡터 임베딩 기반 검색 (옵션화)

**상태:** 검토 필요 — 당분간 보류, 옵션으로 둘 수 있는지 확인
**카테고리:** 추천 알고리즘 / 인프라

### 문제

키워드·역색인 기반 추천이 커버하지 못하는 경우가 있다.
- `관련성경구절` 결측 곡: 가사 주제는 전례 말씀과 통하지만 명시적 매핑이 없어 매칭 실패
- 분위기/감정 질의 ("좀 더 차분한 곡"): 태그가 없으면 처리 불가
- 추천 다양성: 같은 색인 키워드에 걸리는 곡만 반복 노출

### 쉽게 설명 (벡터 임베딩이란)

텍스트를 수백 차원의 숫자 벡터로 바꿔, 의미가 비슷한 텍스트끼리 거리가 가까워지게 하는 기술.
"목자이신 주님"과 "선한 목자" 복음 본문이 서로 다른 단어를 써도 벡터 거리로 "의미 유사"를 판정할 수 있다.

### 이 프로젝트에서 구현한다면

1. **전처리 (1회성)**
   - 곡별로 `요지 + 주제 + 1절 가사`를 한 덩어리로 만들어 한국어 임베딩 모델(ko-sroberta 또는 OpenAI text-embedding-3-small)에 넣음
   - 결과: `data/embeddings/songs.parquet` (495 × 768 ≈ 1.5MB)
   - 주일별 복음/독서도 동일 방식으로 `data/embeddings/lectionary.parquet`
2. **검색 시점**
   - Python으로 주일 복음 벡터 ↔ 495 곡 벡터 코사인 유사도 → 상위 N곡 반환
   - LLM은 후보 리스트만 받음 (토큰 부담 없음)
3. **통합 방식**
   - 단독 필터가 아니라 **보조 점수**. 역색인 1차 + 임베딩 2차 가중합으로 랭킹.

### 도입 시 이점

- 색인 결측 곡에도 적용 가능
- 감정·분위기 자연어 질의 대응
- 추천 다양성 확보

### 도입 시 비용

- **정책 마찰**: 본질이 "자동 추론" → `feedback_no_auto_field_fill.md` 정신과 충돌 가능. 결과를 "후보"로만 쓰는 엄격한 규율 필요.
- **인프라**: 임베딩 모델 호출(OpenAI API 비용 또는 로컬 GPU/CPU), 빌드 파이프라인 복잡도 상승
- **설명 가능성 저하**: "왜 이 곡?"이 "벡터가 가까워서"로 귀결
- **495곡 규모에서는 과잉 가능성**: 키워드+역색인만으로도 상당 수준까지 가능

### 검토 포인트

- **옵션화 구조**: 스킬이 기본은 키워드+역색인으로 동작하고, 플래그(`--use-embedding`) 또는 사용자 명시 요청 시에만 임베딩 계층을 활성화하는 설계가 바람직
- 스키마에 `_embedding_vector_id` 같은 예약 필드는 두지 않기 (오염) → 임베딩 파일은 외부(`data/embeddings/`)에서만 참조
- 도입 판정 기준: D1~스테이지 이후 3개월 사용하며 fail case 누적, 그중 30% 이상이 "색인 결측 + 키워드 불일치"일 때

## C-06: 성경 → 성가 역색인

**상태:** 검토 필요 — 당분간 보류
**카테고리:** 추천 알고리즘 / 색인

### 문제

현재 `색인.관련성경구절`은 84곡(17%)만 채워져 있고, 매칭 시 `recommend-hymns`는 매 곡을 순회하며 LLM이 판정한다. 구절 → 곡의 역방향 조회가 없어, 주일 복음이 "요한 10:27-30"일 때 해당 구절을 인용한 곡을 즉시 뽑을 수 없다.

### 제안 내용

- 파일: `data/scripture_to_songs.json`
  ```jsonc
  { "마태28:16-20": [1, 42, 117], "요한6:51-58": [88, 203] }
  ```
- 빌드: `scripts/build_song_index.py` 실행 시 `관련성경구절` 84곡에서 deterministic 파생 (새로운 추론 없음)
- 성경 키 정규화: `{책약어}{장}:{절시작}-{절끝}` (한글 약어 통일)

### 도입 시 이점

- 주일 말씀 → 곡 조회가 O(1)
- LLM 토큰 대폭 절감 (후보를 미리 좁힘)
- 새 지식을 추론하지 않으므로 정책 위반 없음

### 도입 시 비용

- 현재 매핑이 17%뿐이라 초기 커버리지 낮음 → 보완 없이 쓰면 대부분의 주일이 miss
- 보완하려면 "가사 → 성경 구절" 라벨링이 선행돼야 하고, 이는 **자동 보완 금지 정책**의 대상
- 빌드 스크립트와 songs.json 간 동기화 관리 부담

### 검토 포인트

- 언제 이득이 비용을 넘는가 — `관련성경구절` 커버리지가 50% 이상일 때 체감 효과
- 역색인 자체는 비용이 낮으니 "있으면 쓰고 없으면 패스" 수준의 최소 구현만 먼저 해볼 수도 있음

## C-07: 전례력 3년 주기 (A/B/C년) 캐시

**상태:** 검토 필요 — 당분간 보류
**카테고리:** 외부 의존성 / 캐시

### 문제

`recommend-hymns`가 주일마다 cbck.or.kr에서 복음/독서를 WebFetch한다. 4주를 추천하면 4회 호출.
- 외부 사이트 변경/장애에 취약
- ADR-004(외부호출 최소화)와 마찰
- 토큰·지연 낭비

### 제안 내용

- 파일: `data/liturgy/lectionary_ABC.json`
  ```jsonc
  {
    "2026-04-26": {
      "name": "부활 제4주일(C)",
      "year_cycle": "C",
      "season": "부활",
      "readings": { "1st": "사도13:14,43-52", "2nd": "묵시7:9,14-17", "gospel": "요한10:27-30" }
    }
  }
  ```
- 수집: 사용자 명시 요청으로 3년치 한 번에. miss 시에만 WebFetch fallback
- 크기: 주당 ~200 토큰 × 52주 = 연간 ~10K

### 도입 시 이점

- 주당 WebFetch 4회 → 0회
- 오프라인 동작 가능
- `scripture_to_songs` × `lectionary` 조인으로 "이 주일 독서를 인용한 곡"이 즉시 산출

### 도입 시 비용

- 초기 수집 한 번의 수작업/자동화 파이프라인 필요
- 전례력 변경(특별 기념일 등) 시 수동 패치 필요
- 데이터의 "신선도" 책임이 프로젝트로 이전됨 (cbck.or.kr이 공식 소스)

### 검토 포인트

- 수집 소스 신뢰성: cbck.or.kr을 그대로 캐시할지, 전례력 자체는 가톨릭 공식 ORDO 문서에서 확정적으로 가져올 수 있는지
- 미사 통상문·특별 기념일·대축일까지 캐시 범위에 포함할지
- C-06(성경 역색인)과 결합해야 실질 효과 — 단독 도입 이득은 제한적

## C-08: 템포(BPM) 필드 도입 — 스키마 v2.2

**상태:** 검토 필요
**카테고리:** 데이터 구조 / 추천 알고리즘

### 문제

곡의 빠르기는 '느낌' 태그(활기찬·고요한 등)의 가장 객관적인 근거인데 스키마 v2.1에는 조표·박자만 있고 템포가 없다. 2026-11-05 전수 라벨링에서는 가사 머리말에 OCR로 딸려 들어온 `♩=NN` 표기(64곡)를 보조 근거로만 썼고, 나머지 곡의 느낌은 가사만으로 판단했다.

### 검토 포인트

- `곡목록` 시트에 `템포` 정수 컬럼 추가(v2.2). `export_to_xlsx.py`·`build_songs_json.py`·`songs_index.json`·뷰어 메타 편집(#43) 동반 수정.
- 초기값: 가사 머리말 `♩=NN`/`4분음표=NN`/머리말 숫자(예: `4 4 122`) 64곡 자동 추출. 나머지는 악보(#39) 확보 후 사용자 입력 또는 OMR.
- 추출 후 가사 본문에서 머리말 템포 표기를 제거할지(`/clean-lyrics`)는 별도 결정.
- 모드 B 점수에 "템포 밴드 ↔ 요청 분위기" 가중을 넣을지(예: '떼창·활기' 요청 시 ♩≥100 +2).

### 도입 시 이점

- 느낌 태그의 사후 검증·자동 보정이 가능해짐(♩≤72인데 '활기찬'이면 경고).
- 추천 시 "빠른 곡/느린 곡" 요청을 정량으로 처리.

### 도입 시 비용

- 스키마·빌드·뷰어 세 군데 수정 + ADR 1건. 초기 커버리지 13%(64/495)라 당장 효과는 제한적.
