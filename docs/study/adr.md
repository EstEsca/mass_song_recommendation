# ADR (Architecture Decision Records)

**작성일:** 2026-04-17
**관련 프로젝트 맥락:** 이 프로젝트에서 크롤링 소스 정책, JSON 스키마 채택, 스킬 역할 분리 등 주요 설계 결정을 ADR로 기록함

## 한 줄 요약

프로젝트에서 내린 **중요한 설계 결정을 문서로 남기는 관행**. "왜 이렇게 했는지"를 미래의 자신(또는 팀)이 이해할 수 있게.

## 상세 설명

### 무엇인가

ADR은 소프트웨어 프로젝트에서 **아키텍처적으로 중요한 결정**을 정형화된 짧은 문서로 기록하는 방식이다. Michael Nygard가 2011년에 제안했다.

### 왜 필요한가

- 시간이 지나면 "왜 이렇게 했지?"를 잊게 됨
- 새 멤버(또는 새 Claude 세션)가 프로젝트에 합류할 때 맥락 파악이 필요
- 결정을 바꿀 때, 이전 결정의 이유를 알아야 실수를 반복하지 않음
- 코드는 "무엇"을 말해주지만 "왜"는 말해주지 않음 → ADR이 "왜"를 담당

### 구성 요소

| 섹션 | 내용 | 왜 필요? |
|------|------|---------|
| **제목** | 결정 한 줄 요약 | 빠르게 식별 |
| **상태** | 제안/채택/폐기/대체됨 | 현재 유효한지 |
| **맥락** | 결정이 필요한 배경 | 문제 이해 |
| **결정** | 실제로 무엇을 선택했는지 | 핵심 |
| **대안** | 검토했지만 선택 안 한 것들 | 왜 다른 걸 안 했는지 |
| **결과** | 이 결정의 영향 (긍정/부정) | 트레이드오프 인식 |

### 번호 체계

`ADR-{순번}-{주제-슬러그}.md` 형식. 순번은 시간순 자동 증가.

### 이 프로젝트에서 ADR이 실제로 도움된 순간

- 새 세션에서 Claude가 "왜 벅스를 크롤링 안 하지?" → ADR-001 읽으면 바로 이해
- 스킬을 또 분리할 때 이전 분리 근거(ADR-002)를 참고해서 일관된 원칙 적용
- `songs.json` 스키마를 바꾸고 싶을 때, ADR-003의 대안 목록에서 이미 검토한 사항 확인

## 핵심 포인트

- **짧게 쓴다.** 한 페이지 이내. 설계서가 아니라 결정 기록.
- **결정 후에 쓴다.** 논의 중이 아니라, 결정이 확정된 후 기록.
- **폐기해도 삭제하지 않는다.** 상태를 "폐기" 또는 "대체됨(ADR-XXX)"으로 바꿀 뿐.
- **코드와 가까이 둔다.** `docs/spec/decisions/` 폴더에 코드와 함께 버전 관리.
- **누구나 작성 가능.** 팀 전체의 공유 기록.
