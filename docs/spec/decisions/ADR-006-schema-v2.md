# ADR-006: songs.json 스키마 v2.0 전환

**일자:** 2026-04-25
**상태:** 채택

## 맥락

v1.0(2026-04-16 채택, ADR-003) 운영 4개월을 거치며 누적된 문제:

1. **스키마 복잡도 누적** — 신뢰도 4필드, 외부ID, 가사 6하위 필드, 색인 6필드. 실사용되는 정보보다 관리 비용이 더 큼.
2. **편집 경로 이원화** — JSON 에디터(`server/`) + 엑셀(`song_list_index_sample.xlsx`)로 분산. 에디터는 가사 4필드만 허용, 색인 편집은 엑셀 왕복 필요. 일관성 유지 어려움.
3. **토큰 비효율** — `recommend-hymns`가 매주 songs.json 전체(~30K 토큰)를 LLM 컨텍스트로 로드. 곡 수 증가 시 선형 비용.
4. **자동 재빌드 불가** — ADR-003 2026-04-24 업데이트: 빌드 스크립트가 사용자 편집을 덮어쓸 위험 때문에 병합만 허용. 이 제약이 "원본 raw는 언제 참조하나"를 불분명하게 만듦.
5. **정보 낭비** — `신뢰도.점수/등급/세부지표/실패원인`은 한 번 평가된 후 추천 로직에 실질 반영 안 됨. `외부ID.가톨릭성가번호`도 결측 95%+에 실사용 전무.

`docs/tracker/CONSIDERATIONS.md` C-01이 스키마 고정을 2026-04-16에 결정했으나, 그 후 드러난 위 문제들은 Minor 업데이트로 해결 불가 — **Major 재설계**가 필요.

## 결정

**songs.json 스키마를 v2.0으로 major bump.** 편집 경로·파생 파이프라인·필드 구성을 한 번에 재정의.

### (1) 3계층 데이터 분업

| 계층 | 파일 | 편집 | 목적 |
|---|---|---|---|
| 편집 | `data/source/곡정보.xlsx` | ✅ 사람 + 에디터 | 단일 SSoT 편집 포인트 |
| SSoT | `data/songs.json` | ❌ 파생물 | 스킬이 Read로 접근 |
| 뷰 | `data/songs_index.json` | ❌ 파생의 파생 | 1차 후보 필터 고속 탐색 |
| LLM 입력 | 런타임 Wide TSV | — | 토큰 최소 포맷 |

ADR-003의 "songs.json = SSoT + 편집 가능"을 철회하고 **"xlsx = 편집 SSoT, songs.json = 파생 SSoT"**로 재정의.

### (2) 곡 객체 단순화

**제거**
- `신뢰도.*` (4필드) — 실사용 없음. `data/archive/신뢰도_스냅샷_2026-04-25.xlsx`로 1회 백업 후 영구 폐기
- `외부ID.가톨릭성가번호` — 동일 조치
- `가사.절별`·`가사.절구조`·`가사.출처`·`가사.참조URL`·`가사.확보여부` — 파생 정보, 본문만으로 충분

**평탄화**
- `가사` 객체 → 문자열 스칼라. 확보 여부는 `가사 != ""`로 런타임 판정

**재구성**
- `색인`을 7개 배열 카테고리 + `요약` 스칼라로 재편 (아래)

### (3) 색인 재구성 (8 카테고리 + 요약)

| 키 | 타입 | 설명 |
|---|---|---|
| `요약` | 스칼라 | 40~60자 가사 요지. LLM 사전 분석 |
| `성경` | 배열 | 관련 성경 구절 (정규 키) |
| `성월` | 배열 | `{1~12}월` |
| `시기` | 배열 | 5개 전례시기 vocab |
| `대축일` | 배열 | 공식 대축일명 |
| `역할` | 배열 | 미사 순서 vocab |
| `느낌` | 배열 | 분위기 vocab |
| `키워드` | 배열 | 자유 태그 |
| `곡모음집` | 배열 | 곡이 수록된 성가집/곡집명 (예: `가톨릭성가`, `야훼이레`) |

모두 배열(비어있어도 `[]`). `null` 금지.

**곡모음집 초기화**: v1의 `외부ID.가톨릭성가번호`가 채워진 173곡은 `색인.곡모음집 = ["가톨릭성가"]`로 자동 초기화된다. 이는 `외부ID` 폐기로 사라질 "어느 모음집에 수록됐는가" 정보를 의미 있는 형태로 승계하기 위함. 그 외 곡은 `[]`로 시작하며 `add-tag` 또는 엑셀 수작업으로 추가.

### (4) xlsx 시트 구성

| 시트 | 형식 | 컬럼 |
|---|---|---|
| `곡목록` | Wide | 번호·제목·작곡자·분류 |
| `요약` | Wide | 번호·요약 |
| `색인` | **Tall (EAV)** | 번호·타입·값 |
| `가사` | Wide | 번호·가사 |

색인 시트는 **Tall(EAV)** 형식. 태그 추가·삭제가 행 조작이 되어 사용자의 "로그 남기며 누적" 워크플로우와 정합.

### (5) 편집 경로 일원화

- 엑셀(`곡정보.xlsx`) 또는 에디터(`server/`)에서 xlsx를 수정
- 에디터는 `openpyxl` 기반. 파일 잠금 충돌 시 409 Conflict + "엑셀을 닫아주세요" 안내
- 대화형 `add-tag` 스킬이 `openpyxl`로 색인 시트에 append 가능 (Stage F에서 구현)
- 변경 후 `python scripts/rebuild.py` → songs.json + songs_index.json 재빌드

### (6) xlsx diff 전략

xlsx는 바이너리지만 `.gitattributes`에 `data/source/*.xlsx diff=xlsx` + `xlsx2csv` textconv 등록으로 `git diff`가 셀 단위로 표시되도록.

## 대안

### (a) v1 유지 + 결측 필드만 점진 보완
- 기각. 편집 이원화·토큰 비효율·스키마 복잡도는 필드 보강으로 해결 안 됨.

### (b) CSV 4개 SSoT
- 기각. 엑셀에서 CSV 저장 시 자동 서식 파괴(성경 구절 → 날짜), BOM 이슈, 다중시트 부재. xlsx가 사용자 경험 우위.

### (c) 곡 객체 완전 평면화 (중첩 제거)
- 기각. `색인`·`가사`는 논리적 그룹화가 유용. 7 카테고리를 최상위에 펼치면 필드 수 폭증.

### (d) 임베딩/역색인 선도입으로 색인 단순화
- 기각. 495곡 규모에서는 키워드+역색인으로 충분. 임베딩은 CONSIDERATIONS C-05로 보류.

### (e) 신뢰도를 유지하고 자동 재계산
- 기각. 재계산 로직이 복잡하고, 실사용 없는 정보에 비용 지속 투입.

## 결과

**긍정:**
- 편집 경로 일원화 → 일관성 유지 쉬움
- 곡 객체 크기 ~30% 감소 (신뢰도·외부ID·가사 중첩 제거)
- 추천 스킬 주당 토큰 ~39K → ~8~10K (75% 감축, Stage E 완료 후)
- `색인.요약`이 LLM에 "곡 내용"을 40~60자로 즉시 전달 → 가사 본문 미로드 가능
- Tall 색인 시트가 사용자의 태그 누적 워크플로우와 정합

**부정:**
- v1 데이터의 신뢰도·외부ID·가사 중첩 정보는 archive로 이전, 운영 데이터에서 사라짐 (복구 가능하지만 1단계 추가)
- 모든 가사 관련 스킬(9개) 참조 경로 변경 필요
- 에디터(`server/app.py`)의 쓰기 대상 교체 필요
- xlsx 잠금 충돌이 새 운영 이슈로 등장 (409 Conflict로 완화)

## 적용

### 1회성 스크립트 (Stage A)
- `scripts/migrate_v1_to_v2.py` — v1 songs.json 읽어 v2로 변환 + 백업 생성
- `scripts/export_to_xlsx.py` — v2 songs.json → 곡정보.xlsx

### 상시 스크립트
- `scripts/build_songs_json.py` — 곡정보.xlsx → songs.json (기존 빌더 재작성)
- `scripts/build_song_index.py` — songs.json → songs_index.json (신규)
- `scripts/rebuild.py` — 위 둘 일괄

### 문서 갱신
- `docs/spec/schema.md` — v2.0으로 rewrite
- `docs/spec/vocab.md` — 신규, controlled vocab 정의

### 코드 갱신
- `server/app.py`, `viewer/server.py` — 쓰기 대상 xlsx로 교체
- 가사 관련 스킬 9개 — `가사.본문` → `가사`, `확보여부` → `not 가사` 체크로 변경
